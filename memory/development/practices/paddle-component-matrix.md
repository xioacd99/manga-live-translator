# Paddle组件混搭、分辨率与官方导出适配

- 状态：已解决（本轮协议与适配核验），泛化与目标设备性能待验证。
- 更新日期：2026-11-03（Asia/Shanghai）。
- 范围：同10张历史英文漫画、原人工GT，Linux云CPU、单遍覆盖实验，不是用户M4或浏览器性能。

## 经验与证据

v6官方只有tiny/small/medium，未核到large；v5 server是另代真实型号，不能为了补齐名称将其叫作v6 large。导出格式或不同文件SHA也不等于新的训练型号。

medium固定检测敏感参数后，1024/1536/2048/2560的CER依次约19.68%/13.45%/14.85%/15.85%，分辨率不是越高越准。1536字符错误最少，2048却有更低WER，不能将某一指标的最低值描述成所有质量都最好。

在共同2048流程中，small检测＋medium识别CER14.99%，约18.04秒/页；medium全套CER14.85%，约30.19秒。只有3次编辑差，且小样本单遍不能证明统计优势；拆分检测和识别组件可以暴露全套型号比较掩盖的性能取舍。

v5 server共同2048的CER21.90%、48.00秒；相同small检测器下英文专用22.71%、Latin21.72%，均未优于同检测器的small/medium多语识别器。模型名称、大小或语言标签不能替代实际评测。

## 接入时真正需要核对的部分

- 官方server rec没有ONNX嵌入字典，YAML18383项再加blank/space，与18385输出类别匹配；不可沿用其他模型字典。英文与Latin是不同语言分支，各有自己的字典。
- 官方server的resize_long使用type2：先长边目标缩放、再双边向上取128倍数，不等于Rapid默认round32。初次合成兼容探针曾使用Rapid默认归一化，发现差异后保留诊断，不作为正式官方配置成绩；显式适配并再次合成验证后才进入正式候选。
- 同样的det输入尺寸不保证端到端等价。common组必须先外层resize，供检测和识别裁框共享；仅在det内部放大、识别仍从原图裁框，会引入隐性变量。
- common保留基线padding、legacy分类器、识别batch6和0.5结果过滤。native960适配组单独说明差异，不冒称整条pipeline与PaddleX逐位等价。
- 各组参数在执行前冻结，资源失败保留全部10图分母；不因某个答案差而换字典、阈值或挑选重复轮。

## 验证与限制

v6两阶段13组130次及server/语言6组60次全部完成，共19组190次；输入哈希、模型/字典输出维、CPU线程、实际shape、框与文字桥接、单遍耗时及RSS均独立复核。公开报告只保留白名单统计与参数，不发布原图、完整GT或OCR全文。

目标无OCR输出、字符删除、原始检测行未归属目标是不同遗漏信号，不把部分段落GT的几何代理叫作全页mAP。图表需要把partial/blocked与完成组分开，不因为补齐了10条空记录就误判为10页成功。
