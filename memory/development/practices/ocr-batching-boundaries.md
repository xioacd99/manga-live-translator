# OCR批量、并发与多页模型边界

- 状态：已解决（计时和比较口径）；多页漫画质量仍待验证。
- 更新日期：2026-11-03（Asia/Shanghai）。
- 范围：Linux云CPU、固定英文10图、v6 small参数组、四组各三批；不是浏览器或Mac测试。

## 已观察结果

固定模型与2048/cap4096分辨率后，单worker/ORT intra2的C组暖批44.94秒、首结果6.25秒；双worker的D组暖批42.22秒、首结果11.57秒，采样进程RSS约2.60GB而C约1.51GB。同一目标可能同时改善吞吐并恶化交互延迟，不能只展示整批时间。

识别crop batch从1改为6后，A与B的部分文字结果改变，CER总编辑数404变403；B/C/D完整预测相同。batch大小不是必然不影响输出的纯性能配置，应进入缓存版本身份。当前尚未确定差异具体来自哪个数值或padding环节，不能把可能原因当成已定位的缺陷。

Unlimited-OCR 2社区量化权重通过原生MLX CPU加载，但两页合成探针900.18秒无首token、主进程采样RSS峰值4.61GB，按既定上限结束。没有记录CPU利用率，无法从等待本身判断是慢计算还是内部等待；不能当作漫画精度失败或M4失败。

## 实践

- 分开描述页面任务队列、单页文字裁剪识别batch、同一多页上下文三种机制。
- 初始化完全部worker后开始整批计时；排队/进程间通信保留，文件写入排除。公布第一批与暖批，不把单图连跑时间混入整批表。
- 同时采样的RSS求和仍可能重复计共享页，且采样漏短峰；不是独立峰值简单求和，也不是唯一物理内存。
- 固定输入、哈希、模型、标注及三轮顺序，完整记录所有输出；不挑最好轮。120次身份检查及12轮评分已独立复算一致。
- Unlimited-OCR 2应核对二代PAGE/BLOCK/FORK格式，不从包含旧helper的源码误推二代输出。实际二代转换器采用0–1000坐标，旧一代/999不能直接套用。先前候选研究中这项推断已撤回并更正。
- 多页联合输出可能受页序、邻页和提示影响。若采用该路线，缓存身份需包含上下文，或维持逐页OCR缓存，在用户启用的文字翻译环节引入跨页上下文。

## 限制与证据

样本是历史英文漫画、部分区域标注，不能代表现代漫画总体准确率。只有两轮暖批，D波动明显，不能断言稳健统计优势。线程预算与云CPU不是用户M4的硬件表现；新研究没有改变产品默认。
