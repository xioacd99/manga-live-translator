# 点击启用与本机 OCR 生命周期

## 为什么需要一次安装

Chrome 扩展不能直接执行 Python 或任意本机命令。本方案使用 Chrome 官方 Native Messaging：用户先安装固定本地主机，扩展在用户点击后连接它；主机仅启动同一进程内的环回 OCR 服务，不接受可执行文件、命令或任意 URL。

扩展 Native Messaging 权限与本机宿主安装是两个独立步骤。新增权限只在明确点击时申请；没有宿主时显示安装说明，不默默下载或运行安装程序。模型下载仍是另外一次明确点击，不因为查看状态或打开浏览器而触发。

## 生命周期与隔离

- 自动管理与手动服务分别配置。手动服务仍由用户自行启动/关闭，不会被扩展终止。
- 自动管理使用一个持有的 Native Messaging 连接。其宿主在同一进程内监听 127.0.0.1 的系统分配端口，并生成仅用于该连接的令牌。
- 同一扩展连接复用一个宿主；不同浏览器/配置目录分别启动自己的宿主，端口与令牌不共享。模型文件可共用缓存，但模型内存不跨进程共享，多实例可能多占内存。
- 关闭最后一个普通窗口时，扩展主动断开自己的连接。浏览器进程退出或崩溃造成管道关闭时，宿主自行退出；无需扫描或杀死系统上的 Python 进程。
- 断开时在途 OCR/下载不承诺完成。模型最终文件只有完整校验后原子替换；强制终止可能留下未完成临时文件，不会将其当作完整权重。
- 宿主失败不会后台无限重启。用户重新点击后才重试；授权撤回、忘记设置、切换手动模式也释放自动宿主。

## 用户可见边界

“关闭浏览器”不等于关闭单个标签或其中一个窗口。保留其他普通窗口时服务保持运行；Chrome 后台进程不应让关闭最后窗口后的自动服务继续占用模型内存。崩溃、操作系统终止与窗口关闭是不同路径，测试证据分别列出。

自动管理偏好可保存，临时端口/令牌不持久保存。远端翻译密钥仍保持原有会话内保存行为，因此完整退出浏览器后仍需重新填写翻译密钥。这不是自动登录或自动购买远端调用。

安装与运行步骤见 [服务指南](../../services/local-ocr/README.md)。当前安装器面向 macOS/Linux；不能把 Linux 测试当作用户 Mac/M4 实机验收。Windows 用户保留手动服务模式。

## 验证记录

- 本机 251 项 JavaScript 测试通过，包含自动管理权限请求、单次启动复用、启动中忘记/撤权/关窗、迟到消息、会话恢复和手动模式兼容。新增窗口代次保护，避免关窗检查的旧结果终止用户新开窗口后启动的服务。
- 本机 65 项 Python 测试通过，包含真实宿主子进程/HTTP、精确来源、消息边界、EOF、异常终止、多个宿主与手动服务隔离，以及安装器临时目录测试。阻塞推理/非 daemon 线程使用测试替身，不能声称对真实 ORT 做了中断基准。
- 本机 97 项仓库工具测试、8 项浏览器夹具辅助测试和扩展构建通过。浏览器辅助测试不是实际 Chromium 验收。
- CI 独立运行实际 Chromium → Native Messaging → 生产 Python HTTP。覆盖生产启用消息路径、缺失宿主、最后普通窗口关闭、浏览器退出与实例隔离；没有下载/加载模型、图片或提供方请求。测试使用临时扩展权限和消息调用，不冒充操作真实权限弹窗/自动翻译按钮的人工 UI 验收。
- 本地 Chromium 受既有 Unix 套接字限制，本次没有换路径绕过或重复启动。实际浏览器结果应查看本次提交的 native-lifecycle 与 test CI job；CI 未通过时不能称浏览器已验证。

既有真实四模型与十图回归证据仍见[八模块集成记录](native-pipeline.md)，本次没有重复跑十图或改变识别参数。未验证用户 Mac/M4、Windows 自动安装、真实网站和付费翻译。

## 官方依据

- [Chrome Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)：宿主注册、精确扩展白名单、连接与管道协议。
- [扩展服务工作线程生命周期](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)：Chrome 105 起 Native Messaging 连接可保持工作线程存活。

沿用现有 Paddle/RT-DETR 模型、参数、许可和精度证据，不增加新的 OCR 算法，不把启动自动化说成推理加速。
